# Примеры

Рабочие примеры к модулю. Не куски псевдокода: каждый файл запускается и сам
проверяет, что получилось именно обещанное. Разойдётся обещание с результатом —
пример падает с ненулевым кодом возврата, и это видит CI
(`tests/examples_test.php`).

## Что здесь есть

| пример | цель | где применять |
|---|---|---|
| [problems.php](problems.php) | трейт `LoggerProblems`: проблема в файл и в журнал событий | импорт, выгрузка, агенты, обработчики — всё, что надо потом найти по типу и ответственному |
| [logger.php](logger.php) | логгер модуля принимает исключение, `Result`, `Error`, массив | после вызова D7-метода, в `catch` |
| [throwable.php](throwable.php) | исключение → `\Bitrix\Main\Error` через `Throwable\Manager` | методы, которые возвращают `Result` |
| [log1.php](log1.php) | `Log1Handler`: в файле только последний прогон | разбор одного сценария |

## Как запускать

Два режима, файлы одни и те же.

**Без портала** — ядро подменяется заглушками из `tests/stub/bitrix.php`,
классы модуля и своя копия Monolog подключаются автозагрузкой из
`tests/stub/autoload.php` по тому же соглашению, что на портале. Так примеры
гоняет CI:

```bash
php examples/problems.php
```

**На живом Битриксе** — подключается пролог, модуль берётся
`Loader::includeModule('shef.problems')`, классы находит автозагрузка. То есть
код примера ровно тот, что вы напишете у себя:

```bash
DOCUMENT_ROOT=/var/www/portal php examples/problems.php
```

Режим печатается первой строкой: `Учёт проблем через трейт LoggerProblems [портал]`.
Если там `[заглушки]`, а вы ждали портал — не нашёлся
`<DOCUMENT_ROOT>/bitrix/modules/main/include/prolog_before.php`.

Модуль на портале должен быть **установлен**, а не просто распакован: иначе
пример честно скажет `Модуль shef.problems не установлен` и вернёт 1.

## Как выглядит успешный прогон

```
Учёт проблем через трейт LoggerProblems [портал]

— Класс пишет проблемы
  ok   файл лога по типу проблемы создан = true
  ...

ГОТОВО: problems
```

Код возврата `0`. Любая строка `FAIL` означает, что код разошёлся с тем, что
обещает пример: это находка, а не шум. Ни одного `Warning`, `Notice` или
`Deprecated` в выводе быть не должно — обвязка превращает их в исключение.

## Что примеры делают с системой

`logger.php`, `throwable.php` работают только с памятью процесса, `log1.php`
пишет во временный каталог системы и за собой убирает.

`problems.php` на портале пишет **по-настоящему**: одну запись в журнал событий
(тип `SH_PROBLEMS_SYNC`, модуль `acme.exchange`) и строку в
`sh_problems_sync.log` каталога логов (на BitrixVM — `/home/bitrix/sh_log`). Убирать их пример не станет — это и есть
то, что потом ищут через меню «Учёт проблем». Без портала всё то же уходит во
временный каталог и в заглушку журнала.

## Если добавляете свой пример

Шапка обязана содержать четыре раздела — их наличие проверяет тест:

```
 * ЦЕЛЬ
 * ГДЕ ПРИМЕНЯТЬ
 * ЧТО ДОЛЖНО ПОЛУЧИТЬСЯ
 * ЗАПУСК
```

Дальше `require_once __DIR__.'/_bootstrap.php';`, `title()`, и по шагам:
`step()` — заголовок, `note()` — пояснение, `check()` — обещание.
Заканчивать `done('<имя файла без .php>')`.

`check()` здесь главный: он превращает «должно получиться» в проверяемое
утверждение. Пример без единого `check()` — это комментарий, а не пример.
